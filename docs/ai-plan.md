# AI 能力：怎么让 AI 干活，又不让它碰到令牌

> 状态：**方案，未开工**。这一版（v0.6.9）只做计划，不写实现。
> 本文回答三件事：AI 能做什么、令牌怎么隔离、要不要 CF Worker。

## 一、先划清底线

现有的安全承诺写进了 README 和每个版本的说明里：

- 令牌只在本机加密保管，请求时在内存里解密，用完即弃；
- 无后端、无遥测，请求从设备直连 GitHub（或用户自己配的 API 地址）。

任何 AI 方案都不能悄悄破坏这两条。所以下面所有设计都以一个前提开局：

**AI 永远看不到令牌明文，也永远不直接发请求。**

AI 只做两件事：理解、生成「动作」。真正调用 GitHub 的是客户端。

## 二、三条路，选哪条

| 方案 | 令牌在哪 | 要不要服务器 | 安全边界 | 结论 |
|---|---|---|---|---|
| A. 本地执行器 | 只在设备保险库里 | 不要 | AI 拿到的是脱敏上下文，输出的是可校验的动作 | **主方案** |
| B. Worker 代理（你说的环境变量） | CF Worker 的 secret 里 | 要（用户自建） | 令牌离开设备，但 AI 也看不到，Worker 侧拦越权 | 可选，用于定时任务 |
| C. AI 直接拿令牌调 API | AI 上下文里 | 不要 | **不可接受**：一次提示注入就全丢 | 不做 |

### A. 本地执行器（默认）

```
用户：帮我把这几天提的 issue 分类打标签
  ↓
客户端：抽上下文（仓库名、issue 标题+正文前 500 字、现有标签）
        过滤掉 token / 邮箱 / 密钥形态的字符串
  ↓
LLM：返回 [{kind:'add_labels', repo:'zjkl0330/ghx', number:42, labels:['bug']}, ...]
  ↓
客户端：schema 校验 → 白名单检查 → 显示「将执行 7 个动作」→ 用户确认
  ↓
客户端：用自己的令牌逐个执行，写审计
```

约束：

- **动作是封闭枚举**，不是「帮我调某个 API」。枚举之外一律拒绝，模型编出来的字段直接丢。
- **破坏性动作不在枚举里**。改可见度、删仓库、删分支、强推、改协作员 —— AI 提都提不出来，因为它没有对应的 action 类型。
- **每个动作有风险等级**：`read` 不需要确认，`write` 批量超过 3 个就要确认，`release` 永远确认。
- **模型输出的 repo / number 必须落在当前上下文里**，防止它编一个不存在的仓库去发请求。

好处：令牌一步都没离开设备，也不需要任何服务器，和「无后端」的承诺一致。

代价：模型看不到完整私有代码（只看到客户端愿意给的那部分），复杂任务要分轮。

### B. Worker 代理（你提的「环境变量」）

先把一个容易误解的点说清楚：

> **Worker 里的 secret 不是「环境变量给 AI 用」。** AI 拿到的是**工具定义**（`create_issue(repo, title, body)` 这种），它调工具，Worker 在服务端把 `env.GH_TOKEN` 塞进请求头。AI 从头到尾看不到令牌，只看到工具返回的 JSON。

这条路的真正风险不是「AI 读环境变量」，而是**工具做得太宽**。如果暴露一个 `gh_api(method, path, body)` 的万能代理，那 AI 就有了令牌的全部权限，等于 C 方案换个壳。

所以 B 方案成立的前提是：**工具必须是有语义的白名单**，和 A 方案的 action 枚举一一对应：

```ts
// 可以
POST /tools/create_issue   { repo, title, body }
POST /tools/comment_issue  { repo, number, body }
POST /tools/list_issues    { repo, state }

// 绝对不行
POST /tools/gh_api         { method, path, body }   // 万能代理 = 直接给令牌
```

Worker 侧还要做三件事，缺一不可：

1. **仓库白名单**：`env.ALLOWED_REPOS`（逗号分隔），不在里面的直接 403。
2. **写操作限流**：每小时 N 次，防止模型抽风刷爆。
3. **审计落 KV**：谁在什么时候让 AI 做了什么，事后能查。

另外一个必须摆在明面上的取舍：**B 方案把令牌从「本机」搬到了 Cloudflare**。这不是小改动，它改变了 README 里的安全承诺。所以它只能是**用户主动开启的高级选项**，默认关闭，开启时明确写「令牌将上传到你自己的 Worker」。

### 什么时候才值得上 B

只有当需要「设备不在场也要干活」时才值得：

- 每天早上扫一遍所有仓库的新 issue，生成摘要推给你；
- CI 失败自动开 issue 并 @ 你；
- 多账号汇总的周报。

如果只是「我现在想让它帮我改一批标签」，A 方案更简单也更安全。

## 三、动作枚举（草案）

只列第一版要做的，宁可少而稳。

| 动作 | 风险 | 确认 | 说明 |
|---|---|---|---|
| `summarize_issues` | read | 否 | 输入一批 issue，输出摘要与分类建议 |
| `suggest_labels` | read | 否 | 只给建议，不落地 |
| `draft_release_notes` | read | 否 | 读两个 tag 之间的提交，生成 release 正文 |
| `create_issue` | write | 是 | 标题、正文、标签 |
| `comment` | write | 是 | 评论 issue / PR |
| `add_labels` | write | 是 | 只加不删，避免误清标签 |
| `close_issue` | write | 是 | 必须带 `reason`，不自动 close PR |
| `create_release` | write | **永远** | 只建草稿，发布动作留给人工 |

**不在列表里的**：删除类、可见度、分支保护、协作员、force push、合并 PR。这些一律只能人手点。

## 四、Key 从哪来，存哪

| 东西 | 存法 | 理由 |
|---|---|---|
| LLM API Key | 保险库（现有 AES-GCM，与 PAT 同一套） | 已经是加密的，且有锁屏保护 |
| Worker 的 `GH_TOKEN` | Cloudflare secret | 只能 Worker 读，不进代码库 |
| Worker 的地址 + 调用凭据 | 保险库 | 与 API Key 同级 |

绝不写 `localStorage`，绝不写进 `dist`，绝不进日志。审计日志里只记「动作类型 + 仓库 + 结果」，不记正文。

## 五、分阶段

| 阶段 | 内容 | 版本 | 依赖 |
|---|---|---|---|
| **P0** | 动作框架：schema、校验器、确认面板、审计落盘；**不带任何模型调用**，用固定的假动作跑通全链路 | v0.7.x | 无 |
| **P1** | 接一个模型通道做只读洞察：issue 摘要、stale 清单、release notes 草稿 | v0.7.x | P0 + 用户自己的 API Key |
| **P2** | 写动作落地：create_issue / comment / add_labels / close_issue | v0.8.x | P1 |
| **P3** | Worker 代理（可选）：自建、白名单、限流、审计 | v0.9.x | P2 + 用户有 CF 账号 |
| **P4** | 跨账号：以「当前账号」为边界，跨账号只读汇总，写操作永远单账号 | v0.9.x | P3 |

P0 特意不接模型，是为了先把「校验 + 确认 + 审计」这条安全链路做扎实。链路没跑通就接模型，等于把校验逻辑和模型输出耦合在一起，出问题分不清是谁的锅。

## 六、还没想清楚的三件事

写在这里，免得以后当成「已经决定」：

1. **上下文怎么脱敏才算够。** 现在只想到「按正则剔掉 `ghp_` / `github_pat_` / 私钥块」，但 README 里可能藏着内网地址、私有域名。是否要在发送前给用户看一遍「将要发送的内容」？倾向于是，但这会让每次调用多一步。
2. **多轮对话的状态放哪。** 动作执行到一半失败，重试要能续上，不能从头再来。可能需要一个「会话」概念，落盘。
3. **模型选谁。** 现在不绑死。客户端只认「OpenAI 兼容的 chat completions」这一种形状，用户填 base URL + key + model，这样国内外都能用。响应里只解析 JSON 动作，解析失败就当作普通文本展示，不硬猜。

## 七、为什么这一版不动手

这一版要做的是「主页自述 + 数据看板 + 错误边界」，都是纯本地、纯只读的东西，改坏了最多是显示不对。

AI 那条链不一样：它有写权限。写错一个动作，是往别人的仓库里发评论。所以它值得单独一个版本、单独一轮测试，而不是顺手塞进这一版。
