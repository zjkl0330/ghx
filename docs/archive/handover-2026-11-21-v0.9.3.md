## 一、这是什么

安卓上的 GitHub 客户端，包名 `dev.zjkl.ghx`。纯前端直连 `api.github.com`，没有后端、没有遥测。
用户经常打不开 `github.com`，但 API 通常还通 —— 这就是它存在的理由。

技术栈：Capacitor 7 + React 19 + TypeScript + Vite。没有 router、没有状态库、没有 markdown 库，全部手写。

## 四、跑起来（四条命令）

```bash
cd /workspace/ghx
npx tsc -b                 # 类型检查。必须用 -b，tsc --noEmit 对 project references 是空跑
npx vitest run             # 单测
pnpm build                 # 构建到 dist/
npx vite preview --port 4173   # 端口必须 4173，脚本里硬编码了它
```

打包 APK：

```bash
npx cap sync android
cd android && JAVA_HOME=/opt/jdk-21.0.2 /opt/gradle-8.11.1/bin/gradle assembleDebug
cp app/build/outputs/apk/debug/app-debug.apk /workspace/dist-apk/ghx-X.Y.Z-debug.apk
/opt/android-sdk/build-tools/35.0.0/apksigner verify --print-certs /workspace/dist-apk/ghx-X.Y.Z-debug.apk
```

浏览器验证（**必须有头**，headless 不渲染 `backdrop-filter`，玻璃会拍成色板）：

```bash
xvfb-run -a python3 scripts/verify-archived.py
```

原生逻辑测试（**不需要模拟器**，普通 JVM 就能跑）：

```bash
bash scripts/test-chunked.sh
```

## 五、发版流程

```bash
node scripts/bump-version.mjs 0.9.3     # 传当前版本，自动 +1 并同步 versionCode
npx tsc -b && npx vitest run && pnpm build
npx cap sync android && cd android && JAVA_HOME=/opt/jdk-21.0.2 /opt/gradle-8.11.1/bin/gradle assembleDebug
git add -A && git commit -m "..."        # 信息写「为什么」
```

**推送不能直接 `git push`** —— 见下一节。用：

```bash
TOKEN=<PAT> BASE=<本地上一个提交，如 HEAD~1 或写全 7 位> python3 scripts/push-via-api.py
```

`BASE` 有两个硬条件，写错脚本会直接停下：

1. 必须是**本地仓库里存在**的提交（要 `git rev-parse` 得到）—— 别填远端 sha，本地没那个对象；
2. 它的**树必须与远端 main 的树相同**（脚本会先比对，不一致就退出，防止覆盖别人的提交）。

所以正常情况就是 `HEAD~1`（上一次推送的位置）。连续提交两次再一起推时，`BASE` 要取更早的那个「与远端树相同」的提交。

**tag 也必须经 API 建**（本地 tag 推不上去）：

```python
# POST /git/tags  → 附注对象，object 用「远端」main 的 sha（不是本地 HEAD）
# POST /git/refs  → refs/tags/vX.Y.Z
```

CI 见到 `refs/tags/v*` 才构建签名 APK 并发 Release；普通 push 只留 artifact，Releases 页不会出现新版本。
发版说明直接取 tag 注解，所以内容写在 tag 里。**发出去的 release 一律 `prerelease: true`**（用户要求：只有正式版才提示更新）。

## 六、这个环境的三个特殊之处

**1. `git` 走 `github.com` 不可靠。** 交接当天实测：`curl https://github.com` 回 200 / 0.98 s，
但同一时刻 `git ls-remote gh` 直接 `GnuTLS recv error (-110)`，`git fetch` 132 秒后超时。
所以**不要指望 `git push` / `git fetch`**，一切走 `api.github.com`（`scripts/push-via-api.py`）。
副作用是本地与远端 commit hash 分叉（树相同）；`git reset --soft gh/main` 这条路走不通（fetch 拿不到对象），
只能继续用 API 推。**任何时候都别 force push。**

**2. 没有模拟器、没有 `/dev/kvm`、没有 adb。** 所有 Android 行为都验不了，只能静态断言 + JVM 测试。
所以原生代码刻意拆成「不依赖 `android.*` 的纯 Java」（`ChunkPlan` / `ChunkedFetch` / `NotifText`），这部分能真跑。
涉及通知外观、WakeLock、前台服务、安装器的部分**一律如实说「没在真机验过」**，不要含糊成「已实现」。

**3. 令牌不在环境变量里。** 历史做法是从会话记录里 grep 40 位的 `ghp_...`：

```bash
LOG=/root/.codebuddy/projects/workspace/2f8a7d30-9c21-4f0b-1d61-f9de917ba000.jsonl
T=$(grep -oE "ghp_[A-Za-z0-9]{30,}" "$LOG" | awk 'length($0)==40' | tail -1)
```

这是 workaround，不是好做法。**更稳妥：直接问用户要一个新 PAT**，并且提醒他这枚已经明文出现在对话里好几次、建议撤销重签。

## 七、用户怎么工作（照着做，别自作主张）

- **中文、结论先行、表格优先。** 先说结果再说过程。
- **先侦察再动手。** 不猜、不靠记忆。改之前先 `Read` 真文件、`curl` 真接口。

- **不允许「声称已验证」。** 报全绿之前先确认覆盖到位；发现异常先怀疑自己的验证方法。

- 每次交付说清三件事：**做了什么 / 验证到什么程度 / 还有什么边界**。
